# FIX-041: isolated Windows trial verification by default, 2026-11-08

FIX-041 was blocked because the unelevated Windows sandbox cannot deny reads, so a trial's controller assertions (which run
the scratch project's own tests) ran with the controller's permissions on Windows. The unblock condition was "provide a
vetted Windows isolation backend". The experimental verifier `tests/trials/windows-assert-exec.sh`
([prototype notes](windows-verifier-prototype-2026-11-08.md)) supplies that backend: it runs `assert.sh` with
`codex sandbox` in the elevated Windows sandbox, with no network, a minimal environment, the Codex home and the other
run and evidence folders denied, the controller read-only, and no fallback to the unelevated sandbox.

## What changed

- `assert-exec.sh` uses that verifier **by default on native Windows** (MINGW, MSYS, Cygwin). `TRIAL_WINDOWS_ISOLATION=0`
  opts out explicitly; only the stub-only harness tests (`test-score-outcomes.sh`, `test-score-layout.sh`,
  `test-evidence-retention.sh`, `test-codex-fresh-invocations.sh`) set it. Linux and macOS are unchanged.
- `run-claude.sh` asserts through `assert-exec.sh` like `run-codex.sh` and `score.sh` (it called `assert.sh` directly).
- A verifier exit other than 0 or 1 (2 when the verifier refuses to run, 124 on its timeout) is INFRA_ERROR in
  `score.sh`, `run-claude.sh` and `run-codex.sh`. Before, `score.sh` counted the PASS lines printed before a killed
  verifier as a passing scenario, and the runners called a refused verifier a skill FAIL.

## Checks

Host: Windows 11 Pro 10.0.26300, Git Bash, Codex CLI 0.167.0, elevated sandbox already provisioned.

| Command | Before the change | After |
|---|---|---|
| `bash tests/trials/test-windows-verifier-isolation.sh` (the Done when; its first probe now sets no opt-in) | FAIL: `sandboxed project test did not pass`, because the default ran the probe's project test unconfined and it could read the dummy sentinels | 9 passed, 0 failed |
| `bash tests/trials/test-verifier-failures.sh` (new) | 2 passed, 6 failed: a killed verifier scored PASS, `run-claude.sh` bypassed `assert-exec.sh`, a refused verifier was FAIL | 8 passed, 0 failed |
| `bash tests/run.sh` (regression) | 129 passed (baseline) | 129 passed, 0 failed |

The nine probes: the project-controlled test cannot read or write dummy evidence, login, evaluator or other-run sentinels,
cannot modify the controller, does not see a dummy environment token, and still runs in the scratch repository; an
unusable sandbox mode exits 2 with INFRA_ERROR and runs nothing; the baseline-red report stays readable to the assertions.

The `Windows verifier isolation` workflow (`.github/workflows/windows-verifier-test.yml`) runs the same test on disposable
windows-2022 and windows-2025 runners on every push to `main` and `todo/**`.

## Limits

- Like the Linux profile, the verifier permits general OS reads, and the controller is readable (not writable). Paths
  created after the policy is built, and authentication stored outside the Codex home, are not covered.
- These are dummy-sentinel probes of the verifier, not a fresh-agent Windows batch. The lifecycle batch was rerun with the
  default verifier on 2026-11-08 ([codex-windows-2026-11-08](codex-windows-2026-11-08/summary.md), TASK-045): 2 PASS,
  0 FAIL, 6 INFRA_ERROR. The agent's own sandbox on Windows is unchanged: it still confines writes only and blocks
  the `.git` writes lifecycle needs.
- A Windows host without the elevated sandbox provisioned (`codex sandbox setup --elevated`) now gets INFRA_ERROR from
  every trial assertion instead of an unisolated PASS or FAIL. That is intended.
- FIX-052: the verifier's sandbox user cannot start a Microsoft Store `python3` alias, so Python assertions need
  `TRIAL_PYTHON` set to a regular `python.exe` on such a host; without it the verifier refuses with INFRA_ERROR. It also
  sets `PYTHONNOUSERSITE=1`, so the host's user site-packages cannot shadow a scenario's `tests` package.
