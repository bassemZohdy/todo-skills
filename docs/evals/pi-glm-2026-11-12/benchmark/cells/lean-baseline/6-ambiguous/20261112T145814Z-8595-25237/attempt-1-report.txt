The requirement "Give loyal customers a discount" is missing the core business rule, admits several incompatible implementations, and leaves boundary behavior unspecified. Per the method, I'm stopping before writing any code or files (no `TASKS.md` yet). Questions:

1. **What makes a customer "loyal"?**
   - (a) Order-count threshold, e.g. `orders >= 10` — simple, but ignores tenure and the `since` field; the `>=` vs `>` boundary matters (is the 10th order itself discounted?).
   - (b) Tenure threshold, e.g. customer for ≥ 1 year — rewards long-standing but inactive customers; needs a definition of "now" (see Q5) and makes tests time-dependent.
   - (c) Combination (`orders >= N` **and/or** `since` ≥ some date) — AND is strict, OR is loose; each gives different boundary results for the same data.

2. **What is the discount?**
   - (a) A percentage (e.g. 5% off) — scales with amount, forces a rounding decision (Q3).
   - (b) A fixed amount off — predictable, but can drive the price negative (needs a floor-at-zero rule or a rejection rule).
   - (c) Tiered (bigger discount for bigger loyalty) — more business value, more edge cases to pin down.

3. **Rounding rule for the discounted price?**
   - (a) Round half-up to 2 decimals — money convention most users expect.
   - (b) Round-half-even (Python's default) or truncation — different results exactly at `.005` boundaries.
   - (c) No rounding — leaves float artifacts (e.g. `9.500000000000002`).

4. **Boundary behavior of `amount`:** what should happen for `amount = 0`, negative, non-numeric, or non-int values?
   - (a) Reject negatives with `ValueError`, accept 0 — fail-fast, safest for billing.
   - (b) Pass everything through and just apply the discount — simpler, but a negative amount with a percentage discount *increases* the charge (dangerous in billing).

5. **What is "now" for the `since` date comparison?**
   - (a) Real system clock inside `price()` — no signature change, but tests must compute relative dates and can flake around midnight.
   - (b) An injectable reference date parameter (e.g. `today=None`) — deterministic tests, but changes the public signature.

6. **Missing/malformed customer fields:** if `orders` is absent, or `since` is missing/`None`/not a valid ISO date, should the customer be treated as *not loyal*, raise `ValueError`/`KeyError`, or default (`orders → 0`, missing `since → today`)?
   - Lenient defaults keep `price()` total; strict raising surfaces upstream data bugs earlier.

7. **Discount stacking/interaction:** should the discount be computed on `amount` only (per-call, stateless), or is there any cap (e.g., discount never exceeds some maximum)? Stateless per-call is the simplest reading; caps change behavior on large amounts.

8. **Trust boundary / authorization:** is `price()` called only by trusted internal code with already-validated customer dicts (so no input hardening beyond Q4/Q6), or must it defensively validate the customer shape because callers may pass untrusted data?
