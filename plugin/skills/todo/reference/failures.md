# Test failures, blocking, and a Done when that cannot run

Read on demand from `/todo-continue` ("Test failures"), only when the whole `Done when` or the regression fails after a change, Green fails twice on one test, or a `Done when` cannot run, and from step 2 when it resumes a `[/]` node. Part of the `todo` core skill.

## Test failures

- Diagnose first: reproduce, read the first failing assertion, write one hypothesis in `State:` (`hyp:`), make the smallest change that tests it, rerun. `hyp:` is one line with no `; ` inside (the lint reads what follows it as an unknown item) and stands before `branch`, as the core orders the items.
- At most **3** attempts across sessions (`State:` counter). An attempt is a failed verification run after implementing started, or a failed run that the loop guard makes one (the next items define both); the red run of step 7 (the new test failing before the implementation) is not one. A worker that stopped without a verdict is not one ("A worker that stopped" below).
- **Verification run:** a run of the whole `Done when` (every command of it, as written) made after a change, once implementing started, together with the regression when the regression is run after it. It is one whether or not the regression is run and whether or not you meant it to close the node; when `Done when` or that regression fails, it is an attempt. After a failed `Done when` the regression need not run.
- **Loop guard.** Failed partial runs count too, once implementing started: a run of one of the commands of `Done when`, of one test id, of a subset of its tests or of the regression alone, made after a change. The first one starts a count at 1, and each later one without progress adds 1. No progress means the same first failing test (or another that already failed in this session since implementing started) and no fewer failing tests than the last run of the same command; a run that fails before any test reports is no progress too (unless "A Done when that cannot run" below applies). Each of the 2nd, the 4th and the 8th run of that count is an attempt: raise `attempts` in `State:` and write a new `hyp:`, unless it is the third attempt (then block, below). Fewer failing tests, or a first failing test that has not failed in this session since implementing started, is progress: that run is run 1 of a new count and the attempts stay. A passing run ends the count. A failed verification run is an attempt of its own and is not added to this count. The count is not written to `State:`; a new session starts it at 1.
- **Runs that do not count.** A rerun that only reproduces a failure is not counted, as neither kind of run: nothing changed since the failed run. The first run of a new session that fails on the earlier session's change is such a rerun. A script of your own is never a run of `Done when`, even when it repeats one of its tests: it is not counted and it does not replace a run.
- **Time limit** (`reference/verification.md`): a run stopped at its limit is a failed run: a verification run is an attempt, a partial run is a run of the loop guard's count without progress. Not when the stop came before any test reported for a reason outside the task ("A Done when that cannot run") or the hang is outside the node (below): those rules apply. A stopped baseline run stops the node as a red baseline does. A tool whose longest timeout is below the limit runs at that timeout, and its stop counts as the limit.
- **Escalation** (`reference/routing.md`): with a `Models:` line and work in a subagent (`--delegate`, lanes), each failed attempt raises the next one a tier (`low` → `mid` → `high`), recorded as `tier:`. Without routing, say in the report that a stronger model might help.
- You may change code and the tests this node creates, within the task line.
- Forbidden: editing `Done when`, deleting, skipping or weakening tests, `|| true`, loosened assertions, a narrower command.
- **Outside the node** is a failure that no change within the task line and the tests this node creates can turn green. Examples, not a full list: a flaky test, a regression beyond the task line, a test the node does not own that the change the task asks for breaks, tests or criteria that contradict each other. The reason must follow from the task line, the tests and the project as they are (a contradiction, an arithmetic bound, a test the node may not touch), not from the node's own tries: a target that the node's code has only missed so far (too slow, not found yet), judged from measurements of that code, is not outside the node and uses the attempts. So a time limit that no implementation can meet, by an arithmetic bound, is outside the node, and one that the node's code merely exceeded is a failed run. A failure outside the node blocks at once; the remaining attempts are not used up on it.
- A failure outside the node, and the third failed attempt, block the node: `[!]`, `State:` replaced by a `Blocked:` line in the core format (secrets redacted; no git: a root's `files:`/`docs:` go into the action part as `(files: …; docs: …)`), committed as `chore(backlog): block <ID>` (the sub-items below); stop. Roots block the same way.
  - The `Blocked:` line is one line, and its two arrows are literal. Only the command is in backticks; its error follows outside them. Do not write a raised `attempts` to `State:` first: `Blocked:` replaces `State:`, so the count and the `hyp:` are gone from the file. A block after the third attempt therefore lists each hypothesis in the reason part of the line.
  - The block commit has no body. It holds `TODO.md` and every file the node changed or created, as they are, also uncommitted earlier work of a resumed node; nothing is reverted. It does not hold the generated files of git-flow's clean-tree list, nor scratch files of your own that are no part of the task.
  - The report: a blocked root is not finished, so nothing is drained or merged, also with `--merge`, and no merge commands are printed. Give the step, the `Blocked:` line and the items of step 11 that apply.
- Run commands only under the safety rules in `reference/verification.md`.

## A Done when that cannot run

If the `Done when` command fails before any test executes, for a reason outside the task's behavior (a dotted test path that resolves to a foreign package, a missing runtime or tool, an absent service), the node is not red and the failure is not an attempt. Never edit `Done when`, and never close the node with a different or narrower command. Then:

1. If one empty or declarative file inside the node's own test or source folders makes the command resolve (for example an empty `__init__.py`), add it, name it in the node commit body, and report it under "Adjacent problems".
2. Otherwise stop and report "Done when cannot run" with the command and its first error. Fixing the host (an installed package, a path entry, a service) is the user's call.

## A worker that stopped

A node still `[/]` whose worker is gone (a subagent returned, or a session ended, with no verdict written: `[x]` or `[!]`, or `next: drain` on a root; a usage limit, a crash, a closed session; the error text decides nothing) is **resumable**: not a failed attempt, so `attempts` and `tier:` stay and nothing is blocked. `/todo-continue` resumes it (step 2); a lane coordinator only reports it (`reference/lanes.md`). A node whose branch is checked out in another worktree is not gone: report it and do not resume it.

The order of a resume: first the `git status` check of step 2, which must pass (if it stops the run, make no resume commit), then `git log -2 --format=%s` on the node's branch, read as the log stands before any commit of this run. Unless that log shows `chore(backlog): resume <ID>` twice, the resume goes ahead and starts with the resume commit, made at once, before going on at the step `next:` names: a commit of the node's own `TODO.md`, empty if unchanged, `git commit --allow-empty -m 'chore(backlog): resume <ID>' -- TODO.md` (by path, so staged or changed code stays uncommitted; the command as written needs no `git add`). Any commit that is not a resume commit counts as progress, uncommitted work does not: a node that needs more than two sessions without a commit does not fit one context window (the scope rule). If the log shows `chore(backlog): resume <ID>` twice (resumed twice, nothing committed since), do not resume it again and make no resume commit:

- a leaf that is `mid` or `high`: break it down. Read `reference/plan-step.md`, "Decompose", and follow it for this node. Once the user confirms the children, the node becomes `[ ]` with `State: branch <its own branch> from <the branch it was created from>; next: build children`; until then it stays `[/]`, so every later run offers the breakdown again. Uncommitted changes stay where they are (step 3's clean-tree rule asks about them when a child starts).
- a `low` leaf, or a parent's integration step: block it, `[!]`, with a `Blocked:` line that reads: resumed twice with no new commit → `git log -2 --format=%s` <its output joined with " / "> → decide whether the task or the environment is the problem, then /todo-update <ID> --status ready. The arrows are literal; `<ID>` and the text in angle brackets are placeholders for the node's ID and the two subjects. It is a block like any other: the three sub-items of the block item in "Test failures" apply.

Without git there is no commit to count, so this stop does not apply: resume it and say so in the report.

The node commit of a resumed leaf quotes as `Red:` the failure this session reproduced before its fix, and leaves the line out when it reproduced none.
