# Agent trials

Repeatable scenarios for the skills. `setup.sh` builds a scratch project in a new directory and puts it into a starting state with plain git commands. A fresh agent then follows the skills from that state, and `assert.sh` checks what it left behind. Neither script deletes anything.

```bash
bash tests/trials/setup.sh /tmp/trial-a interrupted-merge
# give the agent the prompt below, with /tmp/trial-a as its only working folder
bash tests/trials/assert.sh /tmp/trial-a interrupted-merge
```

`prompt.sh <dir> <scenario>` prints the exact prompt for the fresh agent (the common instructions plus the scenario's task), so every run uses the same words. The agent works only inside the scratch folder, reads the skills in `.claude/skills/<name>/SKILL.md`, follows them literally, never pushes, never uses `git add -A`, and reports every ambiguity with the quoted text.

## Scoring a batch

A batch is a runs folder with one folder per scenario, `<runs>/<scenario>/`, which holds the evidence of each run. Run one fresh agent per scenario (the runners below lay the folder out), then:

```bash
bash tests/trials/score.sh <runs>
```

`run-claude.sh <runs> <scenario>` writes the batch layout and keeps every invocation's evidence apart: `<runs>/<scenario>/evidence/<UTC time>-<pid>/` with `project.txt`, `prompt.txt`, `command.txt`, `agent.log`, `agent-exit.txt`, `report.txt`, `assert.log`, `outcome.txt` and `SHA256SUMS`. Nothing is overwritten or deleted.

**Where the scratch project is.** An agent must not learn from its working folder which scenario it is in, so `run-claude.sh` and `run-pi.sh` build the project at `<runs>/w-<random>/repo` (a lane scenario's worktrees go to `<runs>/w-<random>/repo.todo`), a new one for every invocation, and write its path below `<runs>` into `project.txt` of the evidence folder. The prompt names only that folder. `score.sh` follows `project.txt` of the newest evidence folder; a runs folder of the older layout, `<runs>/<scenario>/repo`, still scores, and evidence that points to a project that is not there is UNVERIFIED. Two runs of one scenario in one runs folder do not share a project. `TRIAL_REUSE=1` makes an invocation continue the project of the scenario's newest invocation instead (or `<runs>/<scenario>/repo` of the older layout). A `project.txt` that does not name a folder below `<runs>` (an absolute path, or one with `..`) is followed by neither `score.sh` nor `TRIAL_REUSE=1`. The agent's arguments and environment do not name the scenario either: while `pi` runs, its session folder is `<runs>/w-<random>/session-<pid>`, next to the project, and it is moved to `<evidence>/session` afterwards; both runners start the agent without `TRIAL_LABEL` and with `OLDPWD` set to the project. What the layout does not hide: `<runs>/<scenario>/` is a sibling of the project's folder, so an agent that lists the folder two levels above its working folder (`ls ../..`) sees the name of every scenario that was run in that runs folder (in a runs folder that holds one scenario, the only scenario folder listed is the agent's own), and `<runs>/<scenario>/evidence/<id>/project.txt` maps its `w-<random>` folder to the scenario. The name of the evidence folder holds the `TRIAL_LABEL`, and the evidence folders hold the prompts, reports and verdicts of earlier invocations. Inside the project, the `post-checkout` hook of the two race scenarios, which the prompt tells the agent to leave alone, shows an agent that reads it that the base moves once; it does not name the scenario. The command line of the runner, an ancestor process of the agent, names the scenario to an agent that reads the process list. The Codex runners (`run-codex.sh`, `run-codex-multi.sh`, `run-codex-lanes.sh`) still use `<runs>/<scenario>/repo`, so a Codex agent's working folder names its scenario. For the same reason the first commit of every scratch project has the subject `init` and no other commit has (the broken `add` of `ts-baseline-red` and `java-baseline-red` is part of that one commit), every other commit is history that the scenario simulates, with an ordinary subject, and no commit subject, branch name, file, file name, hook or file directly in `.git` of a scratch project holds its scenario's name or one of a list of words that give it away. `trial_names` in `trial-lib.sh` is that scan (`bash tests/trials/trial-lib.sh names <project> <scenario>` runs it on one project): `selftest.sh` runs it on every scenario it builds, and `tests/run.sh` checks that it finds each kind of give-away. Its word list is honest rather than complete. `trial-lib.sh` also holds what the runners and `score.sh` share: the time limit, the choice of the project's folder and the check of `project.txt`.

**Environment.** `TRIAL_TIMEOUT=<seconds>` is the agent's time limit in `run-claude.sh`, `run-pi.sh`, `run-codex.sh` (applied by `codex-exec.sh`) and `run-codex-lanes.sh`, where it is the limit of each agent (default 1500, also when the variable is set but empty; the runner exits with 2 before anything runs when it is not a whole number above 0; where the `timeout` program is missing, as on stock macOS, there is no limit). `command.txt` in the evidence records the limit that was applied, or that none was. A run stopped at the limit ends with agent exit 124, an INFRA_ERROR. `TRIAL_LABEL=<word>` tags a diagnostic run, `TRIAL_REUSE=1` is described above, `TRIAL_CLAUDE_ARGS` adds claude flags (for example `--setting-sources project,local --strict-mcp-config`).

Only scenario names listed in `setup.sh` are counted by `score.sh`; an incomplete scenario folder remains UNVERIFIED, and batch metadata folders are ignored. Each scenario gets one verdict. **PASS**: the agent ran (exit 0, a report) and every check in `assert.sh` passes. **FAIL**: it ran and a check fails. **INFRA_ERROR**: the agent exited non-zero (124 is the timeout), the verifier (`assert-exec.sh`) exited with anything but 0 or 1, so partial output from a refused or killed verifier never counts, or `evidence/<id>/outcome.txt` says `INFRA_ERROR` (write it when you saw a permission denial or sandbox block). **UNVERIFIED**: no repo, or no record that an agent ran; a repository that satisfies the checks without an agent (the read-only scenarios) is never a PASS. The **trial score** is PASS over all scenarios, and every scenario stays in the totals. The check rate is printed too, but it flatters: an agent that does nothing still passes the generic checks. `TRIAL_SKIP=<regex>` leaves out checks the trial environment itself refuses (for example a sandbox that denies writes under `.git/hooks`); skipped checks are printed, and it is never used to hide a skill bug.

`assert.sh` also runs generic checks on every git scenario: conventional commit subjects, `Refs:` and `Reviewed:` on node commits, the skills' merge messages, no tags, tests and lint green, and the CHANGELOG entry format. Read-only scenarios compare against a snapshot `setup.sh` writes to `.git/trial-start` and `.git/trial-refs`.

`bash tests/trials/selftest.sh` (run in CI) checks the harness itself: every scenario sets up, has a prompt, holds nothing that the scan above finds, and an untouched setup **fails** its assert, except the read-only scenarios (`release-ask`, `status-readonly`), where doing nothing is correct. `baseline-red` also fails untouched: its assert needs the agent's report (`TRIAL_REPORT=<file>`, which `run-claude.sh` and `score.sh` set) to name the red baseline, the failing test and a FIX. `stale-claim`, read-only too, fails untouched in the same way: its report must mark the stale claim. The other harness checks are listed under [Harness checks](#harness-checks).

**Codex.** `run-codex.sh <runs> <scenario>` is the Codex twin of `run-claude.sh` (same layout, verdicts and per-invocation evidence, plus `session-id.txt` and `git-state.txt`). It starts `codex exec` through `codex-exec.sh`, which confines writes to the scratch repo (and `<repo>.todo`) and turns the temp-folder exemptions off. Put the runs folder **outside the Windows temp folder**. Reads cannot be denied on the unelevated Windows sandbox, and Git inside it may fail to create branches or worktrees; when the output shows such a block (`infra-signature.sh`) the outcome is INFRA_ERROR, not FAIL, and the matching line is kept in `infra-signature.txt`. `test-codex-isolation.sh` and `test-codex-invocation.sh` need a logged-in Codex and are run by hand; `test-infra-signature.sh` needs none and runs in CI. Findings and results: `docs/evals/codex-2026-11-07/summary.md`. The Linux batch of 2026-11-08 did not use `run-codex.sh`: it ran each scenario in a Docker container with a Codex permission profile that denies the login, prompt and runner paths, and assertions run by the controller outside the agent; see `tests/trials/codex-linux.md` and the boundary limits in the batch `summary.md`. A later audit with dummy sentinels (`docs/evals/linux-boundary-2026-11-08.md`, `test-linux-boundary.sh`) found the profile denies the agent's reads and writes of the login, evaluator and evidence and its network access, but it is not a proof of complete isolation, so the results stay provisional.

**pi.** `run-pi.sh <runs> <scenario> [model]` is the twin of `run-claude.sh` for [pi](https://github.com/badlogic/pi-mono), a minimal coding harness (default model `glm-5.3` on provider `zai`, `ZAI_API_KEY` in the environment; `TRIAL_PI_PROVIDER`, `TRIAL_PI_TOOLS` and `TRIAL_PI_ARGS` override the provider, the tool allowlist and extra flags). Same layout, verdicts and per-invocation evidence, plus `session/` (pi's own session log with every tool call), `versions.txt` (pi, provider, model, thinking level, tools, Node, Java), `verifier.txt` (whether the assertions ran isolated) and `tool-calls.txt`. pi is started with no extensions, no pi skills and no `AGENTS.md`/`CLAUDE.md` discovery, so the only skill text it sees is what the prompt points it at. pi has no permission prompts and no OS sandbox: run it only in a throwaway environment. On native Windows pi has no `bash` tool, only `powershell`, so the default allowlist is `read,powershell,edit,write` and the agent starts Git Bash from it. pi given an allowlist it cannot satisfy answers with no tools at all, so a run with zero tool calls is an INFRA_ERROR, never a FAIL. The assertions go through `assert-exec.sh` like the other runners; on a Windows host without the elevated verifier, `TRIAL_WINDOWS_ISOLATION=0` runs them unisolated and `verifier.txt` says so, so such results are not equal to the isolated batches. Results: `docs/evals/pi-glm-2026-11-12/summary.md`.

**Multi-node trials.** `ts-lifecycle` and `java-lifecycle` need one skill invocation per node. `run-codex-multi.sh <runs> <ts-lifecycle|java-lifecycle>` starts a new `codex exec` for every invocation (the prompt is generated with `TRIAL_ONE_INVOCATION=1`, which tells the agent to stop after one), keeps each invocation's prompt, log, session id and assertion output under `evidence/<id>/invocations/`, and writes `multi-outcome.txt`. A repeated session id, a missing Maven or an unwritable Maven cache is an INFRA_ERROR, never a PASS; `score.sh` reads `multi-outcome.txt`, and a controller stopped between invocations scores UNVERIFIED. With `TRIAL_LINUX_ISOLATION=1`, `assert-exec.sh` runs the controller's assertions with the project's own test processes confined (no access to the login, evidence or network); without it, on Linux and macOS, project tests run with the controller's permissions. On native Windows every runner and `score.sh` send the assertions through `windows-assert-exec.sh` by default, which runs them with `codex sandbox` in the elevated Windows sandbox (provisioned with `codex sandbox setup --elevated`; `TRIAL_WINDOWS_SANDBOX=mxc` selects MXC; no network, a minimal environment with `PYTHONNOUSERSITE=1`, no fallback to the unelevated sandbox), needs the standard `<runs>/<scenario>/repo` layout with the controller outside it, and fails closed with INFRA_ERROR rather than running unisolated. Its sandbox user cannot start a Microsoft Store `python3` alias, so on such a host set `TRIAL_PYTHON` to a regular `python.exe` (the verifier puts a `python3` shim for it first on the sandbox `PATH`); without it the verifier refuses with INFRA_ERROR (FIX-052). `TRIAL_WINDOWS_ISOLATION=0` opts out explicitly; only the stub-only harness tests do. Like the Linux profile, it permits general OS reads and leaves the controller readable but not writable (FIX-041, `docs/evals/fix-041.md`).

**Lane evidence.** In `lanes` and `multi-module`, Git hooks record worktree events. `lane-evidence.sh <repo>` reports worktree counts and `unverified` when events exist, because even interleaved events cannot establish concurrent workers. An optional second argument is a controller-owned activity file with one line per worker: `session-id lane active-start active-end`, using comparable numeric timestamps of independently observed active work. It reports `concurrent` only for overlapping activity by distinct workers in distinct lanes, `sequential` for disjoint activity, and `unverified` for insufficient or invalid evidence. The controller must protect this file and independently establish that its records represent actual activity, not merely process or worktree lifetimes; the script cannot verify provenance. Without such evidence, parallel execution remains unverified. `assert.sh` checks worktree use separately.

**Concurrent Codex lanes.** Codex has no subagent tool, so `run-codex-lanes.sh <runs> <lanes|multi-module>` makes the controller the coordinator's subagent tool (TASK-044). A fresh coordinator (`TRIAL_LANE_PHASE=coordinate` prompt) runs `/todo-continue --all-lanes --merge` through the claims and worktrees and, at item 3 of `reference/lanes.md`, writes each lane's instructions to `<repo>.todo/<ROOT-ID>.brief.md`. The controller accepts a brief only when `<repo>.todo/<ROOT-ID>` is a worktree of the repository on a `todo/<ROOT-ID>-*` branch whose `TODO.md` holds that root, one per lane (`dispatch.txt`). It then starts one fresh `codex exec --json` per accepted brief at the same time. Each may write only its own worktree, the shared `.git` and its own `.git/worktrees/<name>`, which Codex otherwise protects read-only, so Git could not lock the worktree's index. A fresh coordinator then runs the same command again, and its item 0 drains and merges the roots left at `next: drain`. It is not started when a worker exited non-zero (INFRA_ERROR) or left its root without `next: drain` (FAIL, `finish-skipped.txt`), because it would then do that lane's work itself, sequentially. Every agent gets `TMPDIR` and `java.io.tmpdir` inside its own writable Git metadata. The controller stamps each line of every worker's event stream with its own clock as it arrives. `activity.txt` holds one line per worker, from its first tool event to its last, so it does not depend on process lifetimes or Git events, and is passed to `lane-evidence.sh` (`execution.txt`). It uses the Linux trial profile of `codex-exec.sh` (login, controller and every entry of the runs folder except the repository and its worktree folder denied, the evidence included; no network) and must run where that profile is enforced; `TRIAL_LANE_WRITE` adds writable roots such as a Maven cache. Its `multi-module` run, with the attempts that fixed the environment, is in `docs/evals/lanes-codex-2026-11-08/summary.md`.

The overall evaluation used while iterating on the skills is `0.15 x tests/run.sh pass rate + 0.55 x trial score + 0.30 x rubric`, where the rubric is the mean of two independent blind reviews of the skill text (7 criteria, 0-10 each: consistency, unambiguity, completeness, safety, executability, conciseness, testability). Each review deducts about 1 point per medium defect, 2-3 per high and 0.25 per low. A third agent then verifies every medium and high finding against the same text, before any fix: a rejected finding (misread, already resolved elsewhere, or no concrete failure) is credited back at the reviewer's rate, a downgraded one is re-counted as low. Both the raw and the verified rubric are reported.
